# vibecoding-mate 产品需求与技术栈（v2 系统化规划）

> 状态：规划稿 v2（2026-10-02）。**配置 schema 已通过 `doc/13` 网页原型与用户逐项对齐并锁定**；工程代码（src/）仍未改动，Phase A 开工才动。
> 当前固件 v1.8 已发布（CDC + LED + Beep 原型跑通，分支 `mic_ptt_led_key-m_BEEP-LED_CDCs` 已推 GitHub 未合 master）。
> 网页原型：`doc/13_配置网页原型.html`（6 个子页，实时生成 canonical JSON；**布局**后续微调，不影响 schema）。

---

## 1. 产品定位

vibecoding-mate = **「vibecoding 类 APP（Claude Code / Codex / Workbuddy）的状态指示器 + 输入外设」**。

- 宿主 APP 在跑任务时，外设用 **LED / 蜂鸣器 / OLED(后期)** 提示用户三态：
  - **BUSY** = 正在生成对话 / 执行任务
  - **IDLE** = 完成 / 闲置
  - **AUTH** = 需要用户对授权操作
- 设备同时是 **USB 麦克风（UAC2）+ HID 键盘（PTT + 8 宏键）**。

---

## 2. 设计原则（锁死，避免返工）

1. **设备 = 哑执行器**：只认 `SET STATE <busy|idle|auth>` 与配置，不内置任何"vibecoding 是什么"的业务知识。
2. **单一上位机程序**：所有宿主 APP 的状态经它汇聚，经**唯一 CDC 连接**下发给设备（串口独占，禁止多程序抢端口）。
3. **不新增任何 USB 接口**：PID 钉死 `0x4A10`，CDC 永远在 HID 之后；任何描述符改动前用 `tools/decode_uf2_descriptors.py` 静态校验。
4. **协议与配置 schema 带版本号、forward-compatible**：未知键忽略，升 version 才允许 breaking 变更。

---

## 3. 目标架构

```
[ 宿主 APP ] --(hook 脚本 POST 状态)--> [ Host App: /state HTTP ]
                                          |  Device SDK (CDC 唯一持有)
                                          v
[ Config UI (localhost 网页) ] --配置--> [ RP2040 固件 ]
                                   [ TinyUSB 复合(UAC2+HID+CDC) ]
                                   [ Config Store (LittleFS) ]
                                   [ State Executor (BUSY/IDLE/AUTH) ]
                                   [ Drivers: LED / Beep / OLED预留 ]
                                   [ audio(I2S) / HID(buttons) ]
```

- **Host App（单程序）** = Device SDK + Config UI(localhost 网页) + Status Monitor + **状态适配器(adapter per APP)**。
- **设备固件** = TinyUSB 复合 + Config Store + State Executor + 现有 Drivers。

## 4. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 固件 | RP2040 + Pico SDK 2.1.1 + TinyUSB（保持现有复合，**PID 钉死 0x4A10**，CDC 在 HID 后） | 不新增 USB 接口 |
| 固件存储 | **LittleFS**（用户指定）存配置文本；缺失/损坏 → 编译期内置默认 | 见 §9 风险 |
| 固件协议 | 在 `cdc_cmd` 增 `CONFIG GET/SET/DEFAULT` + `SET STATE` + `STATE?`；保留 v1.8 指令 | 带版本号，未知键忽略 |
| 上位机 | **Python 单程序**（沿用 pyserial 工具链，跨平台，Windows 为主） | 内含 Device SDK + Config UI + Monitor |
| 上位机 UI | **localhost 本地 Web 服务**（stdlib `http.server` + 原生 JS，**零重依赖**） | 网页/类网页可视化，无原生 GUI |
| 配置解析 | 与固件同款 JSON 解析；乐谱为 `频率,时长ms;` 文本，两端同款解析 | 一份 schema 两边对齐 |
| 蜂鸣器音量 | **硬件**（电位器 / 物理遮挡），软件不控音量 | 已取消软件 `volume` 字段，避免与旋律播放冲突 |

## 5. 配置规则框架（通用、可增减）

### 5.1 格式
- 文本文件，格式 **JSON**（canonical）。人不必手改：网页 UI 是唯一编辑器；文件仅作备份/移植形态。
- 顶层必须含 `version` 整数字段。

### 5.2 段落结构（可增减规则 —— 你说的"通用成熟框架"）
- 配置由若干**命名段落(section)** 组成；每段是**命名实例(map)** 的集合。
- **新增一类配置 = 新增一个顶层 section**；**新增一个实例 = 在 section 内加一条具名条目**。
- 固件解析时：**未知 section / 未知 key 一律忽略**（forward-compatible）；仅在 `version` 升位时才允许 breaking 变更。
- **缺省规则**：配置缺失/损坏 → 用编译期内置默认（与 JSON 同构），绝不崩溃。

### 5.3 初版 scope（已锁定 · 与 doc/13 网页原型对齐）

```json
{
  "version": 1,
  "device": {
    "led_polarity": "ACTIVE_HIGH",
    "boot_led": "ALL_ON",
    "boot_timeout_ms": 5000
  },
  "states": {
    "busy": {
      "led":   { "standby": "ON",  "blink_on_ms": 0,   "blink_off_ms": 0 },
      "sound": { "enabled": true, "timing": "END",   "count": 3, "loop_interval_ms": 1000, "score": "523,200;659,200;784,350" }
    },
    "idle": {
      "led":   { "standby": "ON",  "blink_on_ms": 0,   "blink_off_ms": 0 },
      "sound": { "enabled": true, "timing": "END",   "count": 1, "loop_interval_ms": 1000, "score": "659,300;784,300" }
    },
    "auth": {
      "led":   { "standby": "ON",  "blink_on_ms": 300, "blink_off_ms": 300 },
      "sound": { "enabled": true, "timing": "START", "count": 3, "loop_interval_ms": 1000, "score": "880,250;660,450" }
    }
  },
  "keys": {
    "ptt":    { "enabled": true, "pin": 2,  "mod": "LGUI",  "key": "KEY_GRAVE",     "behavior": "NORMAL", "click_ms": 1000 },
    "macro1": { "enabled": true, "pin": 0,  "mod": "NONE",  "key": "KEY_ENTER",     "behavior": "NORMAL", "click_ms": 1000 },
    "macro2": { "enabled": true, "pin": 1,  "mod": "NONE",  "key": "KEY_BACKSPACE", "behavior": "NORMAL", "click_ms": 1000 },
    "macro3": { "enabled": true, "pin": 3,  "mod": "NONE",  "key": "KEY_ESC",       "behavior": "NORMAL", "click_ms": 1000 },
    "macro4": { "enabled": true, "pin": 4,  "mod": "LCTRL", "key": "KEY_A",         "behavior": "NORMAL", "click_ms": 1000 },
    "macro5": { "enabled": true, "pin": 5,  "mod": "LCTRL", "key": "KEY_C",         "behavior": "NORMAL", "click_ms": 1000 },
    "macro6": { "enabled": true, "pin": 20, "mod": "LCTRL", "key": "KEY_V",         "behavior": "NORMAL", "click_ms": 1000 },
    "macro7": { "enabled": true, "pin": 12, "mod": "LCTRL", "key": "KEY_L",         "behavior": "NORMAL", "click_ms": 1000 },
    "macro8": { "enabled": true, "pin": 13, "mod": "LGUI",  "key": "KEY_BACKSLASH", "behavior": "SINGLE", "click_ms": 1000 }
  },
  "oled": { "enabled": false, "layout": "PLACEHOLDER" }
}
```

- **device**：
  - `led_polarity`：LED 有效电平（ACTIVE_HIGH/LOW）。
  - `boot_led`：**上电初始化展示**——`ALL_ON`（三灯全亮）或 `ALL_OFF`（三灯全灭）；保持到首个 `SET STATE` 到达（或 `boot_timeout_ms` 超时）。
  - `boot_timeout_ms`：`>0`（默认 **5000**）= 展示这么久后仍没等到 `SET STATE`，就**交还本地控制**（回 v1.8 手感：idle 亮，busy 由 PTT 驱动）；`0` = 永不交还，一直保持展示专心等上位机。
    - **为什么必须有超时**：展示期间执行器是接管 LED 的（否则本地 PTT 逻辑每帧会把 busy 灯拉灭，"三灯全亮"立不住），接管 = 屏蔽本地按键。没跑上位机时若永不交还，用户按 PTT 会以为按键坏了。
  - **无全局声音总开关**：静音 = 把某态的 `sound.enabled` 设为 `false`（见 §5.5）。
- **states**（LED / 声音均**按态独立**配置）：
  - `led.standby`：待机灯光 `ON`(亮) / `OFF`(灭) = 无闪烁时的稳态。
  - `led.blink_on_ms` / `blink_off_ms`：状态闪烁（点亮 / 熄灭时长）；**全 0 = 按 `standby` 常亮/常灭**。
  - `sound.enabled`：该态提示音开关（关 = 静音）。
  - `sound.timing`：`START` = 进入该态时播；`END` = 该态结束（切走）时播。
  - `sound.count`：提示次数；`loop_interval_ms`：多次之间的循环间隔。
  - `sound.score`：**乐谱文本**（`频率,时长ms;...`，例 `523,200;659,200`），空串 = 静音。
  - **已取消独立的 `melodies` 命名旋律表**（M0/M1/M2），乐谱改为每态内联。
- **keys**（PTT + macro1..macro8，结构完全一致）：
  - `enabled`：启用勾选（**禁用宏靠它**，因为 `key` 列表没有"无"选项）。
  - `pin`：GPIO 引脚（硬件绑定，**网页不暴露为可改项**，固件需要）。
  - `mod` =「按键1」修饰：`NONE` / `LGUI`(Win) / `LCTRL` / `LALT` / `LSHIFT`。
  - `key` =「按键2」具体键：`KEY_*`，**列表无"无"选项**。
    - `mod=NONE` → 只映射**单个**按键；`mod≠NONE` → **两个按钮组合**（修饰+主键）同时按下释放。
  - `behavior`：`NORMAL` 正常 / `SINGLE` 单击。
    - **NORMAL**：按下宏 = 按下对应键，**松开宏 = 松开对应键**（跟随物理按住）。
    - **SINGLE**：不管物理按多久、保持多久，**只触发一次**组合键的按下 + 弹起。
  - `click_ms`：**单击时长**，仅 `SINGLE` 生效，控制那一次"按下→弹起"的保持时长。
  - **默认值取自固件 `src/buttons.c` 的 `btn_configs[]`**（见 §5.6）。
- **oled**：后期；本阶段仅占位（`layout: "PLACEHOLDER"`）。

### 5.4 颗粒度对齐（结论 · 已锁定）

| 项 | 结论 |
|---|---|
| LED | 每态独立：`standby`(亮/灭) + `blink_on_ms`/`blink_off_ms`（全 0 = 按 standby 常亮/常灭） |
| 声音 | 每态独立：`enabled`(开/关) + `timing`(开始时/结束时) + `count`(次数) + `loop_interval_ms`(循环间隔) + `score`(乐谱文本)；**无软件音量**（硬件电位器/遮挡） |
| 全局声音 | **无全局总开关**：静音 = 关掉对应态的 `sound.enabled` |
| 按键 | 每键 = `enabled` + `pin` + `mod`(按键1 修饰) + `key`(按键2) + `behavior`(正常/单击) + `click_ms`(单击时长) |
| 按键组合规则 | `mod=NONE` → 单键；`mod≠NONE` → 修饰+主键双键组合；`key` 无"无"项，禁用靠 `enabled` |
| AUTH 态 | 临时覆盖（授权完/超时回 BUSY），设备不感知前态 |
| 初始化展示 | `boot_led`（ALL_ON/ALL_OFF）作为上电初始化态，收到首个 SET STATE 或超时后转正常展示 |
| 提示音时机 | **每态可配**（`timing`），且**绝不执行中常播骚扰**——只在该态开始/结束的边界播 |

### 5.5 状态表现语义（关键约束）

1. **声音是"状态边界提示音"，不是背景音**：按该态 `timing` 决定在**进入态(START)** 还是 **该态结束/切走(END)** 时播放；**BUSY 执行期间绝不常播**——不想在 BUSY 期间出声就把 BUSY 的 `sound.enabled` 设 `false`（或 `timing` 设 `END`）。
2. **"任务完成了"由 BUSY 的 END 提示音承担**：任务结束 = `BUSY → IDLE` 这条边界，此时按 **BUSY** 的 `sound`（默认 `timing=END / count=3`）播"搞定了"并重复催一下。这正是"仅在状态结束时播放"的字面落地。
   - （IDLE 自己的 `sound.timing=END` 是另一条边界：**IDLE 结束**（新任务开始）时才响，默认 1 次短音作"开工"轻提示，不是完成提示。）
3. **AUTH = 需授权提示**：进入 AUTH → 按其 `timing`（建议 `START`）+ `count` 播"需授权"轻催；授权解决回 BUSY 或超时后停。
3b. **一次切换只响一段（优先级规则）**：`START`(进入态) **优先于** `END`(离开态)。
   - 目的：AUTH 是"需要人工介入"的急态，必须保证一进就响；若按 END 优先，`IDLE→AUTH` 会被"离开 IDLE 的开工短音"顶掉，催授权反而听不见。
   - 默认配置下二者不冲突：BUSY→IDLE 时 IDLE 是 END，于是回落到 BUSY 的 END，响的正是完成提示音。
   - 用户同时给 BUSY 配 END、给 IDLE 配 START 时，只会响 IDLE 的那段——这是刻意取舍，写进页面提示即可。
4. **静音**：无全局开关；关掉某态 `sound.enabled` 即静音。**硬件层音量**由电位器/遮挡控制，软件不介入（避免与旋律播放冲突）。
5. **网页试听**：网页端「乐谱」旁的「试听」→ host 经 CDC `BEEP PREVIEW <score>` **临时**下发到设备蜂鸣器试播，不写 LittleFS、不变更当前状态。
6. **AUTH 临时覆盖**由 Host Monitor 维护（§6.4），设备只执行当前态。
7. **上电初始化展示期间由执行器接管 LED**（`host_control=true`），直到以下三者之一发生：
   - 收到首个 `SET STATE` → 转正常状态展示；
   - `boot_timeout_ms` 超时 → **交还本地控制**（`state_exec_release()`：清状态、`STATE?` 回 `NONE`、idle 亮、PTT 恢复驱动 busy）；
   - 收到 `RESET` 或 5s CDC 看门狗超时 → 同上，立刻交还本地。
   > 这不是可选的细节：不接管的话本地 PTT 逻辑会与主循环里 `status_led_set(LED_BUSY, !gpio_get(PIN_PTT))` 抢同一盏灯，实测上电"三灯全亮"只会亮两盏。

## 6. 状态来源（hooks 调研 + 映射）

### 6.1 三工具 hook 机制（2026-10-01 调研结论）
- **Claude Code**（官方）：事件含 `SessionStart` / `UserPromptSubmit` / `PreToolUse` / `PostToolUse` / `PermissionRequest` / `PermissionDenied` / `Stop` / `Notification` / `TaskCreated` / `TaskCompleted` / `SessionEnd` 等。输入 **stdin JSON**，输出 **exit code + stdout JSON 决策对象**（可阻塞 / 允许 / 上报）。
- **Codex CLI**：hooks 体系同源（`SessionStart` / `PreToolUse` / `PostToolUse` / `Stop` / `Notification` 等），架构一致（各事件精确名待逐个核实，**不影响 Phase A/B 开工**）。
- **Workbuddy（Enterprise / CodeBuddy Code）**：27+ hook 事件，覆盖 工具生命周期(`PreToolUse`/`PostToolUse`/`PostToolUseFailure`)、会话生命周期(`SessionStart`/`SessionEnd`/`Stop`/`PreCompact`/`PostCompact`)、代理循环(`SubagentStart`/`SubagentStop`)、授权交互(`PermissionRequest`/`PermissionDenied`/`Notification` 含 matcher `permission_prompt`)。

→ **三者 hook 模型高度一致**：都围绕 `PreToolUse / PostToolUse / PermissionRequest / Stop / Notification / SessionStart / SessionEnd`。

### 6.2 adapter 模式（核心解耦）
- Host 暴露本地 HTTP 端点：`POST http://127.0.0.1:<port>/state`，body `{"app":"claude-code","state":"busy|idle|auth"}`。
- 每个宿主 APP = 一个**极小的 hook 脚本**（shell / Python），在对应事件上向该端点 POST 状态。
- Host 的 Monitor 收到后，按 §5 的配置把状态映射成设备的 LED / 蜂鸣器行为，并 `SET STATE` 下发。
- **新增 APP = 加一个 hook 脚本**，固件 / 协议 / UI 全不动。

### 6.3 三态 ↔ hook 事件映射（建议初版）

| 状态 | Claude Code | Workbuddy | Codex | 备注 |
|---|---|---|---|---|
| **BUSY**（开始工作） | `UserPromptSubmit` / `PreToolUse` | `SessionStart` / `PreToolUse` | `SessionStart` / `PreToolUse` | 用户提交任务即 BUSY |
| **IDLE**（完成/闲置） | `Stop` / `SessionEnd` | `Stop` / `SessionEnd` | `Stop` | 回合结束 → IDLE + 完成提示音 |
| **AUTH**（需授权） | `PermissionRequest` | `PermissionRequest` / `Notification(permission_prompt)` | `PermissionRequest` | 临时态 |

### 6.4 AUTH 临时覆盖规则
- AUTH 视为**临时覆盖态**：进入 AUTH 时记录前一态（通常为 BUSY）；授权解决（下一次 `PostToolUse` 或 `PermissionDenied`/allow）后回到 BUSY；若超时（如 30s 无解决）也回 BUSY。
- 此规则由 **Host 的 Monitor 维护**；设备只执行当前态，不感知"前一态"。

## 7. 协议契约（CDC 指令集 v2，带版本）

保留（兼容 v1.8）：`IDN?` / `LED <BUSY|PLAN|IDLE|ALL> ON|OFF|BLINK` / `LED?` / `RESET` / `BEEP ON|OFF|STOP|<ms>` / `BEEP NOTE <hz> <ms>` / `BEEP PLAY <1-3>` / `BEEP?`。

新增：
- `CONFIG GET` → **多行**输出（因为 CDC TX FIFO 装不下 700 字节的一整行）：
  ```
  < CONFIG BEGIN
  < { ... 若干行 JSON，每行 ≤ 250 字节 ... }
  < OK
  ```
  上位机：读到 `CONFIG BEGIN` 开始收集，直到 `OK` 为止，拼起来就是完整 JSON（**必须能被标准解析器解析**）。
- `CONFIG SET <一行 JSON>` → 校验通过才整体替换；非法 → `ERR 6 <原因文字>`（如 `ERR 6 states.busy.sound.count=99 (0..10)`），且**原配置一字不动**。
  - 只出现在 JSON 里的字段被更新，**未提及的字段保持原值**（支持部分更新）。
- `CONFIG DEFAULT` → 恢复编译期默认。
- 配置改动后立刻 `state_exec_reapply()` 重摆当前态的灯，**不播提示音**。
- `SET STATE <busy|idle|auth>` → 触发状态执行器（按配置驱动 LED/Beep）。
- `STATE?` → 回当前态。
- `BEEP PREVIEW <score>` → 临时试听一段乐谱（不写 LittleFS、不改当前状态），供网页端预览。乐谱格式 `频率,时长ms;...`，与 `states.*.sound.score` 同格式。

错误码（完整表见 `src/cdc_cmd.h`）：

| 码 | 含义 | 触发例 |
|---|---|---|
| 1 | 未知指令 | `FOOBAR` |
| 2 | 行超长 / 半行超时（残缺行已丢弃） | 一行 > 64 字节，或收到首字符后 200ms 无结束符 |
| 3 | 灯名不认识 | `LED FOO ON` |
| 4 | **枚举值非法** | `SET STATE FOO`、`SET BEEP ON` |
| 5 | 缺参数 / 数字解析失败 | `SET STATE`、`LED BUSY BLINK abc` |
| 6 | **配置非法**（A2 起） | `CONFIG SET` 的 JSON 解析失败或字段越界 → 配置**未被采用**，保持原样 |

> `RESET` 语义在 v1.9 收紧为「清接管 + 交还本地」：`STATE?` 回到 `NONE`，灯回到**本地默认**（idle 亮，busy 随后由 PTT 驱动），**不是**回到上电 ALL_ON 展示。5s 看门狗超时走同一条路径。只有**重新上电**才会再走一次 `boot_led` 展示。

> 注：v1.8 的 `BEEP PLAY <1-3>` 预设旋律保留作兼容；正式声音配置走 `states.*.sound`（每态内联乐谱 + 时机/次数/间隔），命名旋律表 `melodies` 已取消。

## 9. 风险 / 坑（锁死）

- **PID 红线**：PID 必须 `0x4A10`；CDC 必须在 HID 之后，否则音频/键盘驱动重装。
- **描述符整体契约**：长度/接口数/端点写错，整个复合设备一起枚举失败；改动前必跑 `decode_uf2_descriptors.py`。
- **串口独占**：CDC 同一时刻只能一个进程打开 → 单程序单连接。
- **配置 schema 版本化**：forward-compatible，升 version 才 breaking。
- **GPIO 全量扫描**：GP0 同时被 UART0 TX + Enter 键占用；GP6 历史被 I²S `dout_pin` 踩过。
- **时钟约束**：蜂鸣器频率公式依赖 `clk_sys=132MHz`，改系统时钟要同步改。
- **LittleFS 可靠性**：掉电写入需原子提交（写临时文件再 rename / 双扇区），避免写到一半掉电变砖。
- **【A2 实测摸清】配置下发的三个坑**（都来自现有 CDC 实现，改配置协议前必读）：
  1. **行缓冲只有 64 字节**（`CDC_CMD_LINE_MAX`），完整 JSON 约 700 字节 → 必须放大到 1024，否则 `ERR 2` 超长丢弃。半行超时 200ms 够用（700B @ 全速 USB ≈ 11ms）。
  2. **TX FIFO 只有 256 字节**（`CFG_TUD_CDC_TX_BUFSIZE`），而 `cdc_reply_line()` 忽略了 `tud_cdc_write()` 的返回值 → 一次回 700 字节会被**静默截断**。所以 `CONFIG GET` 必须**多行分片**输出（每行 ≤ 200 字节），不能单行吐完整 JSON。
  3. **`handle_line()` 会对整行做 `cdc_normalize()` 转大写** → JSON 的键名和字符串值会被破坏。所以 `CONFIG SET` 必须**绕过** normalize/tokenize，用原始行取 payload。
- **【A1 实测教训】"指令回 OK" ≠ "表现正确"**：验收一律用 `LED?` 回读物理电平，不要靠眼睛。首版就是指令层 100% PASS 却漏掉两个灯 bug。
